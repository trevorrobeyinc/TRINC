## The decision

The canonical vault bridge (`Copilot-Everything/bridges/obsidian-copilot-bridge`, socket `vault-bridge.sock`)
stops using the Local REST API plugin (HTTPS on `127.0.0.1:27124`, a Bearer key in the bridge's `.env.local`, the
certificate `config/obsidian-rest-api.cert.pem`). Its six operations (read, create, append, search, open, run a
command) are served by **obsidian-bridge-launcher 0.2.0** in Obsidian's renderer, over the private fd-3 pipe the
launcher opens when it spawns the bridge (`Claude/obsidian-bridge-launcher/src/vaultIpc.ts`). The bridge has no
other backend and no fallback.

Commands run only from the launcher's **exact-id** allow-list (`src/commandPolicy.ts`):
`copilot:super-summarize-to-note`, `copilot:summarize-to-note`, `command-center:run-workflow`,
`command-center:toggle-pipeline-sidebar` and `command-center:analyze-current-note`. The bridge's
`security.executeCommandAllowlist` can only narrow that list.

Who decided, in their words, typed in that session or this one:

- *"i would like Local REST API with mcp plugin from obsidian retired from the current setup which idk if it is
  yet or not"*, then, of the backends put to them, **"Launcher's private pipe (Recommended)"**. The other options
  are in that session's transcript; this record does not restate them.
- For the allow-list: **"Use exact ids"**, and, shown what exact ids do not settle (below), **"keep all five"**.

## Why

- The plugin is the last TCP listener in the vault lane after bridges-uds (`ops/security/bridges-uds-2026-11-24.md`
  kept it on purpose), and its key sits in two files any same-user process can read.
- Its `POST /commands/{id}/` runs **any** Obsidian command for whoever holds the key, and a RunJS-style plugin is
  one command away from running code in the renderer. The pipe has no port and no key, and the launcher decides
  which commands run.
- The old backend ignored HTTP status, so a missing note or a refused command came back `ok: true`. Failures are
  now failed tool results.

## Considered and rejected

- **A prefix rule** (`command-center:*`): it admits whatever Command Center registers later, including
  `command-center:cancel-workflow`, which stops a running research run without asking. Left out on purpose.
- **A suffix rule** (`copilot:*-to-note`): every Copilot custom prompt registers such an id, and the bridge's own
  `create_note` can add prompts to that folder.
- **What exact ids do not settle** (found in review): an id fixes which command runs, not what it does. The two
  Copilot ids run whatever prompt their notes hold, and `create_note` can rewrite those notes. Their runner is a
  chat call with no tools, so the reach is a prompt of the client's choosing through a configured model, not code
  execution. Put to the operator with the recommendation to drop those two (nothing calls them through the
  bridge); the operator kept all five ("keep all five", 2026-11-25). The list changes only on their word.

## How it was checked

Three adversarial passes, each a set of reviewers whose every finding a second agent tried to refute:

1. The first cut (four lenses: contract, security, runtime, gates) returned 41 findings plus 5 from its verifiers.
   The one high finding, confirmed by all four: the launcher decoded each fd-3 read on its own, so a UTF-8
   character split across two reads became U+FFFD and the damaged note text still parsed. That line predated the
   change, which made it reachable.
2. The fixed tree (four lenses: are the fixes real, new launcher defects, new bridge defects and test strength,
   records) returned 42 findings plus 5. The two medium ones were in the deploy and rollback procedure. The low
   ones included a read cap that broke append confirmation on large notes, refused command ids written in clear
   to the audit log, over-long ids no longer audited, and timeouts marked retryable for a create or a command.
3. The round-3 tree (three lenses: the code, the strength of the tests, this procedure walked against the real
   scripts) returned 32 findings plus 2. The one medium: the test for the create race could not catch the removal
   of the check it named; hand mutants that delete each check now fail it. The rest, low and nit, included an
   oversized body reported as INTERNAL_ERROR instead of PAYLOAD_TOO_LARGE, open preferring a note the same text
   links to over the exact one on disk, search folders skipping the bridge's guard, and a dozen fixes to the steps
   below.

What the code now does, in short:

- One `StringDecoder` for each end of the pipe, and each frame joined once. Every write carries the body's sha256,
  and the launcher writes nothing on a mismatch.
- Notes are found in another letter case and before Obsidian indexes them, as the REST plugin found them; an append
  to a file it finds only on disk keeps that file's text, and a writer racing a create is caught by a second look.
- A note body is capped in UTF-8 bytes (16 MiB, PAYLOAD_TOO_LARGE) so that whatever is written in one call can be
  read whole, and an append is confirmed by a tail read, which no size cap limits.
- `open_vault` opens the exact note asked for, waiting briefly for the index when it is on disk but not indexed,
  and otherwise resolves link text; it never leaves an empty tab on a refusal. Search folders must exist, in
  several spellings, and pass the bridge's guard first.
- The audit log never holds note text or a client's id in clear: refused command ids are recorded by length and
  sha256 (with whether Obsidian has such a command, and the class of a `runjs:` or `app:delete` probe), only the
  five allowed ids appear as text, and only refusals the bridge's own guard should have made, or a damaged body,
  are recorded as `LAUNCHER_VAULT_REFUSED`, by path digest. The bridge audits a launcher refusal as `ALLOWLIST_DENY`
  reason `launcher_refused`, and an over-long id as `too_long`. Calls that fail the bridge's schema before any check
  appear only as `TOOL_CALLED` and `TOOL_FAILED`.
- The probe refuses a launcher that serves another vault, or does not say which (`vault_mismatch`,
  `vault_unverified`). A timeout is retryable only for reads, searches, opens and appends, and a backend that cannot
  recover in this bridge process (no pipe, a closed pipe, an old launcher, another vault) makes every refusal
  non-retryable. The bridge's path guard also refuses a link inside the vault that points into one of its hidden
  folders.

Tests: the launcher gained its first suite (`npm test`, `node --test --experimental-strip-types`, the pattern
Command Center uses; 91 tests against a fake vault), and the bridge's grew from 12 spec files and 91 tests at
`6f271f0` to 20 files and 155, including a text-level contract test that reads the launcher's sources, a test of a
launcher refusal through the real backend path, and a guard that the REST backend stays gone.

## 2026-11-27: `append_note` no longer strands its idempotency key

Built by Claude Code in `/Users/myhome/Worktrees/TRINC/append-started-row` (branch `claude/append-started-row`, cut
from main `eb30de0`) for the Security Everything session `local_47856c50-392e-4d4d-921c-bd2d5721dbe5`, from the
engine read-back session's finding of 2026-11-25. The launcher-refusal rule below was put to the operator with its
trade-offs; they handed it back ("You write it"), and Claude chose the named set of three reasons, which keeps a
reason the launcher adds later ambiguous until someone looks at it.

- **The bug.** `appendNote.ts` writes a STARTED ledger row before the backend runs and moved it to AMBIGUOUS only
  for `CLI_TIMEOUT`, `CLI_EXIT_NONZERO`, `QUEUE_TIMEOUT` and `LAUNCHER_IPC_TIMEOUT`. Any other failure left it
  STARTED with nothing written, and a key the durable ledger has seen is only ever reconciled, so every later call
  with it ended `AMBIGUOUS_WRITE_REQUIRES_DECISION`. For a note that did not exist yet, the reconcile read also got
  `NOTE_NOT_FOUND` and answered retryable **true**, so a caller that repeats the same call never stopped.
- **The fix.** A failed append frees its key (`ledger.forgetUnwritten`, which never deletes a COMMITTED or
  RECONCILED row) only when the failure proves the note untouched: the selector refused (`NO_CAPABLE_BACKEND`,
  `BACKEND_SELECTION_STALE`); the request never left the bridge (the IPC client marks a call refused on an
  already-closed pipe as unsent, and the backend reports `requestSent: false`); or the launcher refused with
  `path_refused`, `invalid_params` or `too_large`, which `vault.append` raises only before writing
  (`launcherContract.spec.ts` checks that against the launcher's source). Every other failure is now recorded
  AMBIGUOUS, the four timeouts included. A reconcile read answered `NOTE_NOT_FOUND` counts as "no marker"
  (retryable false), as the REST backend's empty read did.
- **Not the inverse of the old list.** Freeing every key but the four timeouts would append text twice: a pipe that
  closes with the append in flight, an error thrown by the write itself and an answer the bridge cannot read may all
  come after the launcher wrote. Tests pin each of them to "reconcile, never write again".
- **Checked.** `src/tests/appendNoteRetry.spec.ts` (new, 10 tests) runs the real selector, backend, IPC client and
  SQLite ledger against a fake launcher; with main's `appendNote.ts` 8 of the 10 fail, the three cases that wrote
  nothing on `AMBIGUOUS_WRITE_REQUIRES_DECISION`. With 14 more tests in five spec files the suite is 179/179 (from
  155); 30 of 30 hand mutants of the changed lines were killed. `npm test`, `tsc --noEmit`, `lint:transport`,
  `npm run build`, `lint-transport-monorepo.sh --strict`, and the engine's adapter and schema tests (35/35) pass.
- **Written down, not fixed.** (1) "Read the note, no marker" (retryable false) and "could not read it" (retryable
  true) share `AMBIGUOUS_WRITE_REQUIRES_DECISION`, and the engine's adapter passes on only the code and
  `retryable`; a distinct code for the second would change the contract the engine's recipe keys on, so it is the
  operator's call with the engine's owner. (2) An append the launcher confirmed but whose marker the tail read
  then misses (over 16 KB appended by someone else within the second it looks, or the note rewritten) also answers
  retryable false, which that recipe reads as "missing": a new key there appends twice. (3) No cancellation: the
  launcher has no cancel method and the renderer finishes a write the bridge gave up on, so a first attempt can
  still land after a same-key retry was refused; callers wait out the ~35 s append budget first. (4) Keys stranded
  before the deploy stay stranded in the live ledger; only a new key gets past them.
- **Deploy.** Nothing else moves: once the commit is on main, step 4's rebuild of the main checkout's `dist/` and
  a 'Restart bridge'. `verify.sh` will not call the old build stale (it compares `dist/index.js` with `src/index.ts`,
  which this change does not touch); after the rebuild `dist/idempotency/ledger.js` contains `forgetUnwritten`.
- **Changes after that deploy, on the operator's go.** The engine's `appendIdempotencyKey` comment
  (`Trevor Robey Intelligence Network Citations/openclaw-bridge/mcp/obsidian-bridge-mcp/index.js:196-211`) still
  describes the stranded key, a missing note answering retryable true, and this fix as pending: true of the live
  bridge until the rebuild.
