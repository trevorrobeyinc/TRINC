## 2. What the engine actually does (the part you said you didn't understand)

You type a research question into **Obsidian Copilot chat**. That hands off to an Obsidian plugin (`openclaw-command-center`) which runs a small local bridge on a private Unix socket (`command-center.sock`, a file only the operator's account can open; it left TCP port `:8799` on 2026-11-24). The plugin launches a Node program — `scripts/run-workflow.js` — which is the **OpenClaw research engine**. It runs one of the **biomedical workflow templates** (drug-discovery, pharmacovigilance, clinical-trial-landscape, target-validation, rare-disease, general, trial-design-benchmark) — or, since 2026-10-21, one of three **business-lane** templates (business-research-pack, cost-reduction-analysis, market-landscape) that run through the same engine and the same citation gate on business evidence (see §4: not yet run live). For each step it calls a large language model, pulls in biomedical tool data, scans the text for citation identifiers, and — once the citation gate passes — **writes the results back into your Obsidian vault itself** as a set of linked notes (Overview, one note per agent role, Quality Audit, Dataset Card, the integrity deliverables verbatim (citation integrity, graveyard memo, search coverage and reproducibility manifest, plus the design benchmark when the run produced one), and a deterministic Graph Analysis from the Medical Zettelkasten MCP). That write happens **headless** — it does not need Obsidian open, and the engine runs the same way from a plain terminal. When Obsidian *is* open, the Command Center plugin finds those notes (it never writes them twice) and adds the enrichment stages: the chat bubble, Miyo indexing, the LLM Zettelkasten linking appended to the synthesizer note, and the research-memory ingest. *(Rewired 2026-09-22 — before that the plugin was the only writer, and it only fired for runs it had dispatched itself while Obsidian was open, which had never happened: no run had ever reached the vault.)*

## 3. Citations — what's real, and the one real gap

**Real:** the engine *extracts* citation identifiers with regular expressions (`openclaw-bridge/core/citation-extractor.js`) and embeds them in the notes, and there are quality gates that check citation density before a report is considered done.

**Updated 2026-06-12 — a zero-fabrication CITATION-INTEGRITY layer now ships.** The engine no longer just extracts identifiers; it checks that the cited ones are *grounded in the source records actually retrieved at runtime*, and screens cited DOIs and PMIDs for retraction. What's now live:
- **Runtime grounding gate (report-level).** `agent-engine` persists `fetched_citation_ids` (the identifiers actually retrieved at runtime by tool-prefetch) plus a per-task `citation_verification` block; `buildPrompt` carries an ABSOLUTE-RULE "ZERO FABRICATION" clause (never invent a PMID/NCT/DOI — say "[no verifiable citation found]" instead). `workflow-engine.executeMissionStep` then runs `verifyReportCitations` (`openclaw-bridge/core/citation-gate.js`): every identifier cited in the assembled report is cross-checked against the union of runtime-fetched ids. A cited id is **grounded** if it was in fetched evidence, else **ungrounded** (likely model-introduced). Per the never-hallucinate doctrine (operator ruling 2026-07-10) the gate returns a **three-state verdict**, not a silent boolean: **PASS** (grounded ratio ≥ `minGroundedCitationRatio`, now a required value in `config/agent-config.json` = **0.75**, the B-grade floor); **UNVERIFIED** (`PHASE30_CITATION_UNVERIFIED` — ratio below the floor); **INSUFFICIENT_EVIDENCE** (`PHASE30_CITATION_INSUFFICIENT_EVIDENCE` — **zero runtime evidence was fetched**: a recorded honest-zero that now BLOCKS rather than auto-passing, which is the doctrine hole this ruling closed); and **NO_CITATIONS** (`PHASE30_CITATION_NONE` — evidence fetched but the report cited nothing). Only PASS ships. **Where the `[UNVERIFIED]` marks land (corrected 2026-11-14):** on PASS the *shipped sections themselves* carry an `[UNVERIFIED]` mark at **every** mention of an untraced identifier, placed after a whole link (`annotateSubtaskOutputs`, span-based since T1-3; it used to mark only the first raw-text match per id; since T2-20, 2026-11-16, after the whole construct holding it: a markdown link whose text holds brackets or whose title holds a parenthesis, an angle-bracket autolink, an HTML link or tag, a bare or scheme-less URL, and for a reference definition after each use of its label, so the definition stays valid; constructs are read with the engine's marks set aside, so a mark inside one fails the re-read below), and so do the report's Citation Summary, the sample preview (whose summary is cut only at a line end, so a mark never parts from its identifier; Tier 1 review, 2026-11-14) and `tables.csv` (`grounded_in_run` = no); a section whose marks cannot be written stops the run (`PHASE30_CITATION_ANNOTATE_FAILED`). Only the engine's own appended verification list (its exact header and intro sentence) is exempt from marks; a heading of the same name the model writes is not (Tier 1 review). The workflow dir gets `citation-verification.json` on every verdict and `report-annotated.md`, an internal annotated copy, whenever an id is ungrounded or retracted. A section the gate cannot read is a failure (`PHASE30_CITATION_SECTION_UNREADABLE`), never an empty section. The floor is read **fail-closed** (missing/invalid config → the strict `0.75` default plus a `min_grounded_ratio_unconfigured` warning), replacing the old hardcoded `0.34` / dead `0.5`; since T1-6 configuration can only **tighten** it (a value outside 0.75–1, including `0` or `null`, falls back to 0.75), and PASS is decided on integers (`verified × 1000 ≥ round(floor × 1000) × total`), never on the rounded display ratio. The ratio spans every identifier type the extractor reads, not only PMID, NCT and DOI.
- **The written forms read (T1-4, 2026-11-14; corrected by the Tier 1 review the same day).** PMIDs in a `PMID:`/`PMIDs:` label (each item of a comma or semicolon list, also when the first item sits in a wiki-link or markdown link, as the vault enricher writes it: `PMID: [[PMID-a|PMID: a]], b`), a `PubMed ID:` label, a bare `PubMed:` label before a number of 5+ digits, a PubMed record URL, and bare cells under a table column headed exactly `PMID`; NCT numbers with an optional space or hyphen, also after `_` (italics) or a digit (a longer digit run is dropped, never cut); DOIs bare, behind `doi:` or any doi.org spelling, and inside publisher URLs (a `?query`/`#fragment` cut), de-duplicated case-insensitively; PubChem CIDs only under an uppercase `CID` on a word boundary. PMIDs start at 1, so `PMID 0` is never read. The read-only replay over 191 stored reports and notes moved no sealed release's ratio (all seven still PASS) and found no CID over-capture. **Read since T2-17 (2026-11-16):** a later list item followed by a word, and a final item after `and` or `&`, when it has 5 or more digits (a shorter number there stays prose: "10 patients", "and 2019 data"); a `PubMed IDs:` list in full; a label with markdown emphasis or a `#` (`**PMID:**`, `PMID: **n**`, `PMID #n`), whose first item must have 5+ digits so the packager's own count lines ("**PMID**: 8 verified") are never read; `CIDs:` lists; `UniProt ID:` and `UniProt accession`; and, inside a URL only, a publisher's path after a DOI is cut (`/full`, `/abstract`, `/pdf`, `/epdf`, `/fulltext`, `.pdf`, and the version of a 10.1101 DOI in a bioRxiv or medRxiv URL), while a bare DOI is never cut (operator default D10: the real versioned OSF DOI `10.31234/osf.io/r2fnz_v2`). **Read since T2-16 (2026-11-16):** ISRCTN numbers (bare, spaced, hyphenated, or in an isrctn.com URL); PMCIDs (the `PMC` token, a `PMCID:` label with or without the prefix, a PMC or Europe PMC URL; a PMCID's digits are never read as a PMID, and a PMCID is grounded only by a retrieved PMCID); EudraCT numbers only after an `EudraCT` label or in an EU register URL (operator default D6). **Not read:** a lowercase `cid:` (operator default D9), an EU CT number, a EudraCT number with no label or URL, a patent number, an author-year reference with no id. The read-only replay over 240 stored files (87 release deliverables, 40 workflow-dir files, 24 research outputs, 89 vault notes) added 39 PMIDs, all from release sample previews' bold-label lines, lost none, found no T2-16 form, and left all eight sealed `report.md` identifier sets unchanged. An identifier written in a form not read is invisible to the gate, the marks, the screen and re-resolution. **The review's one high finding (F1):** before the fix, a synthesizer or report_generator section's `PMID: a, b` list lost every item after the first, because the enricher links the first and the list stopped at its `]]` (sealed `offer-7e373eb2de36a7a2e73e7c1c` report.md:332 lost four PMIDs).
- **Grounding by type (T1-5, 2026-11-14).** `agent-engine` also persists `fetched_citation_keys` (`TYPE:ID`), and the gate grounds a cited id only by a retrieved record of the **same type** (a retrieved PubChem CID 2244 no longer grounds a written `PMID: 2244`). A mission whose evidence records predate the keys falls back to number-only matching; the gate result and the ledger record which applied (`grounding_match`: `type_and_id` / `id_only`). **Shown on a live run (updated 2026-11-16):** the first armed run after this change, `workflow-e255cb68727f683268c754db` (`drug-discovery-full`, offer `offer-d5ada9a79a258deeb9513730`), recorded `grounding_match: type_and_id` with a PASS verdict in its `citation-verification.json`. That meets the condition this line set before copy says "by type"; changing customer copy is still the operator's decision.
- **Packaging requires the gate's own record (T1-1, 2026-11-14).** The engine writes the verdict beside the mission (`workspace/missions/<id>/artifacts/citation-verification.json`): `pass:false` before every throw after the gate and when a later quality audit fails, `pass:true` only after the last rewrite of the shipped sections, pinning the sha256 of `mission-summary.json` and of every section. `generate-offer.js` (via `offer-builder`) refuses a mission without a passing record, one whose files changed since, or one with no `status.json`; so a `run-research-task.js` mission, or one sealed before this date, cannot be packaged until it is re-run. A record is never written by hand. **The quality audit (Tier 1 review, operator pick D1):** a passing record says `quality_audit: "pending"` until the workflow's quality step passes (then `"passed"`; a workflow with no quality step records `"not_applicable"`), and the offer builder refuses `"pending"` (`PHASE19_MISSION_QUALITY_AUDIT_PENDING`), so a run killed or cancelled between the gate and the audit cannot be packaged with a density audit that never ran.
- **Retraction screen — Crossref + PubMed, cross-checked (widened 2026-07-10, escalation + notice-disambiguation same day).** Cited DOIs are checked against Crossref `/works/{DOI}` (`openclaw-bridge/mcp/crossref-retraction/crossref-retraction.js`); cited PMIDs against PubMed E-utilities `esummary` (`openclaw-bridge/mcp/pubmed-retraction/pubmed-retraction.js`, publication type `Retracted Publication`); AND every cited DOI is reverse-resolved DOI→PMID (E-utilities `esearch <doi>[AID]`) and cross-checked against PubMed; and since T2-16 (2026-11-16) a cited PMCID is screened through the PMID its PMC record lists (or, with none, its DOI), and a retracted one is named as the PMCID (`retracted_pmcids`, block reason `retracted_pmcid`; operator default D8). A report citing ANY retracted paper hard-stops (`PHASE30_CITATION_RETRACTED`). Since T2-1 a screen request a registry did not answer is asked once more after 2,000 ms, so a passing throttle no longer leaves an id unscreened. Fail-soft everywhere: a network error yields no NEW retractions, so a blip can never wrongly block a report. **Per-DOI rule: `retracted = pubmedRetracted OR (crossrefFlagged AND NOT pubmedNotice)`.**
  - **Why all three legs (verified live 2026-07-10 — do NOT "simplify").** Crossref's `update-to`/`relation` signal is **inconsistent and ambiguous**: (1) it is ABSENT on `10.1016/S0140-6736(97)11096-0` (**Wakefield 1998, retracted 2010**) — the DOI screen alone scores the most notorious retraction in medicine as **clean**; PubMed marks it `Retracted Publication`, and the DOI→PMID escalation catches it. (2) It is AMBIGUOUS: `update-to: [retraction]` appears on both the Surgisphere original retracted paper AND the Wakefield **retraction notice** `10.1016/S0140-6736(10)60175-4`, so Crossref alone false-flags the notice. PubMed's pubtype (`Retraction Notice` vs `Retracted Publication`) disambiguates, and a Crossref flag is overridden only when PubMed positively says notice. (3) Many citations carry a **PMID and no DOI** (e.g. GeneReviews, PMID 20301295) and never reach Crossref at all.
  - **Which Crossref field means what (T1-7, verified live 2026-11-14; fixtures in `tests/fixtures/crossref-probe-2026-11-14/`).** The 1998 paper's retraction is in its own **`updated-by`** (type `retraction`, source `retraction-watch`), a field the screen did not read before; the 2010 notice carries `update-to` naming the 1998 paper. The Crossref leg now marks a DOI **retracted** on its own `relation["is-retracted-by"]`, an `updated-by` entry of type exactly `retraction` (Crossref serves the Retraction Watch entries there), or an in-place retraction (an `update-to` retraction naming the work itself, as on the Surgisphere original). An `update-to` retraction naming **another** work marks the record a **notice**, which never trips the block. Partial retraction, withdrawal and expression of concern are listed in the ledger and never block (operator default D3).
  - **PubMed's editorial notices (T2-2, 2026-11-16; fixtures in `tests/fixtures/registry-probe-2026-11-15/`).** The PubMed leg also reads a docsum's reference types: "Expression of concern in" is listed in the ledger as an expression of concern recorded by PubMed, and a "Retraction in" link on a record not marked `Retracted Publication` is listed as a partial retraction or an update not yet made, since PubMed marks neither apart (a paced probe found no publication type or filter for a partial retraction). Both are ledger flags and never block (Tier 1's operator default D3 and Tier 2's D14); a retracted paper still blocks on its publication type.
  - **Coverage (T1-7).** Every cited DOI, PMID and (since T2-16) PMCID is screened, in chunks of 50 up to a ceiling of 500 per class (it used to stop silently at 50). A DOI counts as screened only if Crossref holds it or PubMed resolved it to a PMID with a definitive verdict; anything else, including a DOI no retraction source holds (operator default D2) and anything beyond the ceiling, is **named** as unscreened in `citation_verification`, in the manifest (flag `retraction_screen_incomplete` → `DELIVER_WITH_FLAGS`, never a block) and in the ledger ("Retraction screen: INCOMPLETE, N of M cited DOIs, PMIDs and PMCIDs not screened"). The bundle says "retraction-screened" only when the screen was complete.
  - **Exact-match rule.** Both `Retracted Publication` and `Retraction Notice` are matched **exactly**. Citing a retraction notice is legitimate and must never hard-fail a report; a substring match on "retract" would. Never loosen either to a regex.
  - **Fail-closed on the retraction axis.** Under a PubMed outage a Crossref flag STANDS (conservative — block rather than risk shipping a retraction). Coverage under an outage (corrected by the Tier 1 review, 2026-11-14): a cited PMID whose PubMed check fails is unscreened and named, so `checked` goes false; but a DOI that Crossref holds still counts as screened when its PubMed cross-check reached no verdict (the T1-7 rule, kept by the operator, pick D2). Those DOIs are counted (`retraction_dois_crossref_only`), and the bundle, the ledger and the listings say they were screened against Crossref alone instead of naming PubMed for them. This differs from the coverage CLAIM, which fail-softs.
  - **Parenthesized-DOI extraction fix (same day).** The DOI extractor previously excluded `)`, truncating Elsevier/Lancet legacy SICI DOIs (`10.1016/S0140-6736(97)11096-0` → `10.1016/S0140-6736(97`) into a malformed id no registry could screen. It now captures balanced internal parens and trims only an unbalanced trailing `)` from prose wrapping. This is what makes the Wakefield DOI screenable at all.
  - **PMID width fix (same day).** The PMID pattern was `\d{6,9}`, which (a) MISSED legitimate sub-6-digit historical PMIDs — PMID 1 is a real 1975 paper — leaving them invisible to both the grounding gate and the retraction screen, and (b) TRUNCATED a 10+ digit run to a 9-digit prefix that can collide with a different real PMID. Now `\d{1,10}(?!\d)`: covers PMID 1 through 10 digits (centuries of headroom past the current ~41M/8-digit max) and drops an over-long run rather than mis-capturing a prefix. Measured impact on the grounded-ratio denominator across all shipped bundles: **zero** (real reports cite 7–8 digit PMIDs that both patterns already matched) — this is a correctness fix for edge cases, not a scoring change.
  - **Residual gap (honest caveat, narrowed 2026-11-14).** A retracted paper cited **by DOI only, NOT indexed in PubMed**, whose Crossref record carries no retraction relation, no `updated-by` retraction and no in-place `update-to`, is still missed; since T1-7 the Retraction Watch entries Crossref serves are read, so this is a retraction recorded in neither Crossref nor PubMed. A paper cited **by PMID alone** is checked in PubMed only (there is no PMID→DOI leg), so a retraction only Crossref records is missed for it (stated in every ledger since the Tier 1 review). The Retraction Watch bulk dataset itself (~65 MB) is not used.
- **DOI extraction fix.** The DOI regex now stops at non-DOI terminators and strips trailing sentence punctuation, so `]]` / `;` / `.` are no longer captured (which had deflated the grounded ratio and duplicated DOIs).
  - **Markdown-emphasis fix (2026-09-22, from the first gated run started in Copilot chat).** A citation the model wrote as `**Lynch et al., 2004 (doi: 10.1056/nejmoa040938)**` was captured as `10.1056/nejmoa040938)**` — the `)` sat behind the `**`, so the unbalanced-paren trim never reached it — and the re-resolver sent the literal `)**` to doi.org (404 → UNRESOLVED → the whole run BLOCKED, while the same DOI's plain mention was VERIFIED). `normalizeDoiId` now also trims trailing `*`/`~`; regression test in `tests/core/citation-extractor.test.js`. The other UNRESOLVED id in that run, `NCT07442490`, is a genuine 404 in ClinicalTrials.gov — the gate caught a model-introduced trial id exactly as designed.

**Honest framing (the brand is zero-fabrication):** citations are **grounded in the source records actually retrieved at runtime**, **retraction-screened (cited DOIs against Crossref and PubMed via a DOI→PMID cross-check, cited PMIDs against PubMed, cited PMCIDs through their PMC record's PMID or DOI), with any paper the screen could not reach named**, **and — as of the post-research integrity layer — independently re-resolved per identifier against their issuing public registries when the report is assembled** (the date is stated in the bundle; a re-check at delivery is not built).

**✅ GAP CLOSED — the resolver is BUILT, WIRED, and VERIFIED (validated 2026-07-10).** The former "only true product-quality hole" no longer exists. What was previously spec'd is now shipping:
- **Resolver.** `openclaw-bridge/mcp/citation-reresolver/citation-reresolver.js` (`RESOLVER_TABLE_VERSION = "2026-11-16"`) re-resolves each cited identifier against its issuing registry: **PMID** → NCBI E-utilities `esummary.fcgi`; **NCT** → ClinicalTrials.gov API v2, asked in batches of 200 through `filter.ids` since T2-6 (a number the batch echoes back exactly is VERIFIED; one it leaves out goes to `/studies/{id}`, whose 404 stays the only UNRESOLVED; the API pads a short number, so only an exact echo counts); **DOI** → Crossref `/works/{doi}/agency`, with a `doi.org` HEAD fallback; since T2-16 **PMCID** → NCBI `esummary` (db=pmc), **ISRCTN** → the ISRCTN query API (its record page answers alike for a real and an invented number), **EudraCT** → the EU register's text download, where an empty answer is UNCHECKED and never UNRESOLVED because the register does not publish every trial (operator default D7). Since T2-3 a **ChEMBL** id resolves through `chembl_id_lookup`, which knows every entity type (INACTIVE is UNRESOLVED, operator default D13), a **UniProt** 404 is UNRESOLVED, and a PubChem 503 is recorded as a throttle. Each id is stamped **VERIFIED / UNRESOLVED / UNCHECKED** with its `http_status` and `resolved_url`. **Fail-soft by construction: a non-definitive answer is UNCHECKED, never a false VERIFIED;** since T2-1 a lookup a registry did not answer (a timeout, a network error, a 5xx, a throttle) is asked once more after 2,000 ms, and only a definitive answer replaces UNCHECKED.
- **Wiring.** `workflow-engine.js` calls `reresolver.resolveAll(cites)` → `buildReproducibilityManifest()` → writes `reproducibility-manifest.json` + `.md`; `deliverable-packager.js` ships both into `deliverables/` and registers `artifactRefs.reproducibility_manifest`. **Since T2-6 (2026-11-16)** the cites are the report's identifiers plus the NCT numbers the graveyard memo and the design benchmark list (both built just before, still fail-soft); each manifest row names the deliverables it appears in (`sections`), and `summary.by_section` keeps per-deliverable counts, so `report.md`'s own figures stay report-only while the decision judges every row. An NCT only those files list counts as retrieved in the run (their fetchers retrieved it). Until this date those files' NCT numbers were never looked up; the order form still says they are not separately re-resolved, and is unchanged pending the operator's answer (Q1).
- **Delivery decision.** `BLOCK` on any UNRESOLVED id (the fabrication signature; since T2-6 a memo or benchmark NCT too, operator default D15), any retracted DOI, PMID or PMCID, or a gate hard-fail; `DELIVER` only at 100% VERIFIED **and no attribution mismatch and a complete retraction screen**; otherwise `DELIVER_WITH_FLAGS` (`flag_reasons`: `unchecked_over_threshold`, `attribution_mismatch` and/or `retraction_screen_incomplete`). The UNCHECKED comparison is made on integers, so a single UNCHECKED id always forfeits `DELIVER`.
- **Attribution check (2026-11-04).** `openclaw-bridge/core/citation-attribution.js`, run by `reresolver.checkAttributions` after re-resolution: where the report names a single author beside a VERIFIED DOI/PMID ("X et al.", a year-anchored "X & Y"), that name — and a year written next to it — is compared with the registry record (Crossref `/works/{doi}`; the NCBI docsum the PMID check already reads). A name that is on no author list for that work is flagged: `attribution_mismatch` → `DELIVER_WITH_FLAGS`, an "Attribution check" section in the manifest, and `[ATTRIBUTION MISMATCH: registry lists …]` inserted beside the identifier in the shipped sections (operator decision: flag and mark inline, never block). It checks **who wrote the cited work and when, not what the report says about it**; most citations carry no adjacent author and are recorded "not checkable". Since T2-19 (2026-11-16) the name-to-identifier distance is measured without the engine's own marks, so an `[UNVERIFIED]` mark between them can no longer leave a flagged work unmarked; an identifier in a reference definition is not checked (T2-20). First live finding: run #7 (ALS) credited 6 of the 7 papers in its reference table to the wrong authors, all with real, retrieved, resolving identifiers.

**You MAY now assert per-citation external re-resolution to a buyer** — this supersedes the previous "do not assert" instruction. Assert it with these honest bounds: (1) re-resolution confirms the identifier **resolves to a source record**, not that the source's scientific conclusions are correct; (2) identifiers with no definitive answer are reported **UNCHECKED**, never verified; (3) the re-resolution pass is itself fail-soft — a resolver/network failure logs `citation_reresolution_failed`, and since T1-8 (2026-11-14) the bundle still seals but with a **fallback manifest**: every cited id UNCHECKED with reason `reresolution_error` and `reresolution_completed: false`, which the buyer ZIP (`build-buyer-zip.js`), marketplace staging (`distribute.js`) and the engine export (`export-release.js`) all refuse ("re-resolution did not complete; re-run the order"); the packager refuses a gated bundle with no manifest at all (`PHASE19_RERESOLUTION_MANIFEST_MISSING`). Before this a crash sealed a bundle with no manifest (`offer-bcaf2746298f5280fde747f0`). An UNRESOLVED id, by contrast, hard-fails `PHASE30_CITATION_UNRESOLVED`.

**What each delivery path refuses (T1-2, T1-11, 2026-11-14; heading corrected by the Tier 1 review — the paths do not refuse the same things).** `scripts/_delivery-checks.js` holds the refusals once: a file changed after sealing, no manifest, a delivery decision that does not allow shipping, an UNRESOLVED id, an incomplete re-resolution pass, any ChEMBL identifier, and retired wording. Of `workflow.json` it passes on only the workflow, template and offer ids and the quality score (Tier 1 review: the file carries local paths, run inputs and every step's result), its adapters document the real `tables.csv` columns, and its training-data target never turns a sentence citing an untraced id into a "factual" record. The workflow's own export step runs the same checks as `export-release.js` (T2-14, 2026-11-16; before this it checked only the approval, and the armed proof run of 2026-11-16 zipped and recorded an export of a release `export-release.js` refuses): a refusal writes and records nothing, and the run completes with the reasons under `artifacts.export_refused` in `workflow.json`. **Re-packaging never deletes evidence (T2-12, 2026-11-16):** offer ids are deterministic, and packaging the same source again used to delete the old release with its approval and evidence ledgers; `generate-offer.js` now refuses while the release holds `release-approval.json`, `submission-evidence/` or `delivery-evidence/` (`PHASE19_RELEASE_HAS_EVIDENCE`), and `--supersede` first moves that release whole to `releases/_superseded/<offer>-<n>/`.

**No per-citation evidence ledger exists.** `security/interaction-log.json` is chain-hashed but is reset at the start of every workflow (`executeWorkflow`), so it is not an evidence ledger, and the bundle has no "provenance chain": its integrity mechanism is the flat per-file SHA-256 seal (`manifest.json` + `checksums.txt`, written by `finalizeBundle`). The chain-hashed ledgers that do exist are the Phase 22/28 submission and delivery evidence ledgers, which record exports and deliveries, not citations.
